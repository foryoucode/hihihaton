# Северный код

Планирование восстановления станции: Go-backend, Vue 3, PostgreSQL, sqlc и Goose. Два точных метода — основной алгоритм потоков на Go и OR-Tools CP-SAT в отдельном Python-сервисе. Нейросети, обучение и старые веса удалены.

## Быстрый запуск

Из корня репозитория:

```bash
docker compose up --build -d --wait --remove-orphans
```

Сайт: `http://localhost:8080`. Compose запускает три сервиса: `app`, `db`, `solver`. Четыре учебных CSV импортируются в PostgreSQL автоматически при первом запуске. Повторный запуск не заменяет импортированные данные. Ключи API не нужны.

```bash
docker compose logs -f
docker compose down
```

База сохраняется в volume `postgres_data`. `docker compose down -v` удалит её. Другой порт: `PORT=8081 docker compose up --build -d --wait`.

Пароль локальной PostgreSQL задаётся через `POSTGRES_PASSWORD`, по умолчанию `north-local`. Порт базы и OR-Tools на хост не публикуется. Приложение предназначено для локальной работы без авторизации.

При обновлении предыдущие SQLite-файлы и volume `station_data` не удаляются. История из SQLite автоматически не переносится; новая версия использует PostgreSQL.

## Импорт CSV

На сайте откройте «Импорт CSV» и выберите каталог, поставщиков, предложения и отчёт станции. Файлы — UTF-8, допустим BOM, разделитель `;`. Исходные примеры находятся в `north-code/data`.

До записи проверяются ID, типы и единицы, числа, связи между файлами, согласованность бюджета/срока и свойств объектов. Четыре файла записываются одной транзакцией в отдельную версию набора. При ошибке текущий набор остаётся рабочим; частичные данные не сохраняются.

Каталог, предложения, поставщики, объекты и потребности хранятся в связанных таблицах PostgreSQL. Расчёты читают данные из БД. Каждый сохранённый план связан с ID исходного набора. При открытии истории сайт загружает именно этот снимок, поэтому последующий импорт не меняет старый план.

## Методы расчёта

Оба метода используют одинаковые требования и сравнивают планы по кортежу:

```text
(превышение бюджета, -число восстановленных мобильных пунктов, стоимость)
```

Все обязательные объекты должны быть восстановлены. Мощности не складываются; сравниваются одинаковые типы и единицы. Проверяются доступная мощность установленного устройства, температура, общий остаток предложения, доставка плюс установка. Доставка считается один раз поставщику. Работы выполняются параллельно.

**Основной Go-алгоритм:** перебор наборов объектов и поставщиков, минимальный стоимостной поток, безопасные нижние оценки для отсечения. Полностью работает без Python. При отмене/тайм-ауте не выдаёт незавершённый результат за оптимальный.

**OR-Tools CP-SAT:** бинарные переменные закупок, использования поставщиков и восстановления объектов. Для каждого количества мобильных пунктов доказывается минимальная полная стоимость. OPTIMAL и INFEASIBLE учитываются отдельно. FEASIBLE/UNKNOWN при тайм-ауте не выдаются за оптимум: API возвращает 504.

Go повторно проверяет каждый возвращённый план непосредственно по исходным данным БД, независимо от подготовленных кандидатов. Проверяются все характеристики закупок, обязательные потребности, остатки и сроки; стоимость пересчитывается сервером. Непроверенный ответ не сохраняется.

Если обязательное восстановление невозможно, показываются потребности, оставшиеся незакрытыми в одном из максимальных частичных распределений, с указанием отсутствия подходящих предложений или дефицита общего остатка.

Ограничения демонстрационного алгоритма: до 10 необязательных объектов и 12 поставщиков. Перебор в Go экспоненциальный, лимит запроса — 110 секунд; OR-Tools использует общий лимит 90 секунд на все количества пунктов.

## Контрольный результат

На исходных CSV оба метода дают **2 482 000 ₽**: оборудование — 2 212 000 ₽, доставка — 270 000 ₽. Восстанавливаются B01, B02, B03, M01, M02, M05 к 14-му дню. Остаток — 118 000 ₽.

Минимальная стоимость для 0–5 мобильных пунктов:

```text
1 824 000; 2 027 000; 2 231 000; 2 482 000; 2 782 000; 3 633 000 ₽
```

На странице «Сравнение» оба метода рассчитываются на текущем наборе с одинаковыми бюджетом, сроком и отключёнными поставщиками. Показываются статус, число пунктов, превышение, стоимость и время; статических ML-метрик нет.

## Разработка

Нужны Go 1.23.4+, Python 3.12+, Node.js 20.19+ и PostgreSQL 16. Go-драйвер PostgreSQL не требует GCC.

Из `north-code`:

```bash
bash scripts/install.sh
```

Задайте `DATABASE_URL` либо стандартные `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE`, `PGSSLMODE`, затем:

```bash
bash scripts/start.sh
```

Go применяет миграции Goose и при пустой базе импортирует учебный набор. `SOLVER_URL`/`SOLVER_PORT` задают адрес/порт OR-Tools, `APP_ADDRESS` — адрес Go API. `START_ORTOOLS=0` запускает только основной Go backend. Для разработки интерфейса: `cd client && npm run dev`.

## sqlc и Goose

- `backend/db/migrations` — схема PostgreSQL.
- `backend/db/queries` — SQL-запросы импорта, чтения и истории.
- `backend/internal/repository/sqlc` — код, созданный sqlc v1.29.0.

```bash
bash scripts/generate.sh
source scripts/env.sh
cd backend
go run ./cmd/migrate status
go run ./cmd/migrate up
```

`down` откатывает миграцию и удаляет таблицы; применять только на тестовой базе либо после резервного копирования.

## Проверки

С подключённой тестовой PostgreSQL:

```bash
bash scripts/test.sh
```

Интеграционные Go-тесты создают отдельные временные схемы и удаляют только их. Проверяются транзакционный откат после частичной записи, multipart CSV-импорт, чтение из БД, сохранение старых наборов и истории, Goose, оба способа обработки ответа решателя, независимая проверка ограничений, сравнение Go-алгоритма с полным перебором маленьких задач. Python-тесты проверяют CP-SAT, общие остатки, совместную доставку, целостность объектов и тайм-аут.

## API

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/health` | PostgreSQL и доступность OR-Tools |
| GET | `/api/data?dataset_id=...` | Последний либо выбранный снимок данных |
| POST | `/api/import` | Multipart: equipment, suppliers, offers, station; необязательное name |
| POST | `/api/search` | equipment_type, capacity, temperature, dataset_id |
| POST | `/api/calculate` | method (`exact` / `ortools`), budget, deadline, disabled_suppliers, dataset_id |
| GET / POST | `/api/plans` | История / расчёт и сохранение с name |
| GET / PATCH / DELETE | `/api/plans/:id` | Чтение / переименование / удаление |

Python-сервис предоставляет только `GET /health` и `POST /solve`. Всё пользовательское API и работа с БД находятся в Go.
